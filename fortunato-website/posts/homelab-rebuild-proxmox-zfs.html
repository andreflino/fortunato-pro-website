From a Dead NAS to a Hardened Media Stack: A Homelab Rebuild

A failed Synology VM update turned into a full storage redesign, a live migration, a mystery performance bug, and a lesson about private-tracker ratios I didn't see coming

I started this session trying to check disk space on my home NAS. I ended it having rebuilt half my homelab. That's usually how the good ones go.

The setup

Two Proxmox hosts on the home network: one running a Media-Server VM (Radarr, Sonarr, Prowlarr, Bazarr, qBittorrent, Jellyfin, Plex, plus a full observability stack crammed on for good measure), the other running an Xpenology VM — Synology's DSM, virtualized on non-Synology hardware — as the actual NAS.

The Xpenology VM is the one that started this whole thing.

When the NAS died

DSM had tried to auto-update itself to version 7.3. The bootloader (Arc Loader, a Redpill-based loader that lets DSM run on generic hardware) didn't have config support for that combination of model and DSM version yet. Ramdisk patch failed, the loader dropped into a recovery shell, and the whole thing entered a loop — silently drifting its own IP address in the process, which is how I first noticed something was wrong.

What followed was a genuine debugging saga: updating the loader itself, discovering the update kept failing because /tmp (sized off the VM's RAM) was filling up with stale build artifacts, fighting a keyboard-layout mismatch in the browser console that made typing / impossible, and eventually landing on the real suspect — a likely kexec incompatibility between the emulated model's decade-old platform kernel and the actual 2024-era CPU underneath it.

Lesson

Xpenology on very new CPU silicon is a real risk. Check community compatibility threads for your specific CPU generation before committing to it — or just run genuine hardware / TrueNAS instead of virtualizing a decade-old kernel on top of silicon it was never built for.

Starting over with ZFS

Rather than keep fighting the loader, I cut losses: destroyed the Xpenology VM, wiped the passthrough disk, and built a proper ZFS pool instead.

# Single disk today, mirror-ready for later zpool create -f nasdata /dev/sda # Carve out a quota'd dataset for the media VM zfs create -o quota=1T nasdata/mediaserver

Structuring it this way means when a second disk shows up, zpool attach turns it into a live RAID1 mirror with zero downtime — a lot cleaner than mdadm's degraded-array dance.

Migrating a live service

The actual Media-Server VM needed to move onto this new box without losing anything. The two Proxmox hosts aren't clustered, so no live migration — an offline backup/restore instead:

# Stream the backup straight to the other host, no local disk needed vzdump 111 --mode stop --compress zstd --stdout | \ ssh proxmox-nas "cat > /nasdata/mediaserver/vm-111-backup.vma.zst"

--mode stop sounds scarier than it is — Proxmox only pauses the VM for about 17 seconds (a snapshot-consistent freeze) before resuming it and streaming the backup in the background. 180GB, 46 minutes, essentially zero perceived downtime.

Then I hit a genuinely obscure bug: qmrestore failed with couldn't determine archive info on a file I could prove was 100% valid. Turns out its archive-info parser expects Proxmox's own backup filename convention (vzdump-qemu-<vmid>-<timestamp>.vma) — a custom filename silently fails detection even when the content is perfect. Renamed the file, restore worked immediately.

Restored with a fresh MAC address so the new copy could boot alongside the still-running original for verification, then did the actual cutover: shut down the original, matched the new VM's MAC to it (the guest's network config was static and tied to the MAC), and it reclaimed the exact same LAN IP with zero downstream reconfiguration.

The real bottleneck

Everything felt sluggish afterward. First instinct was CPU — stopped the whole monitoring/CI stack that had been riding along on the same VM, since it wasn't earning its keep there anyway. That helped, but not enough.

top told the real story: 77% I/O wait. The physical disk backing everything was a single 7200RPM spinning drive, and it was serving double duty as both the VM's OS disk (Docker, SQLite databases, systemd, logs — all small random I/O) and the live qBittorrent download/seeding traffic. Mixing random OS I/O with torrent I/O on a spinning disk is a recipe for seek thrashing.

# Live-move the OS disk to fast storage, VM stays running throughout qm disk move 111 scsi0 local-lvm

OS disk moved to the host's NVMe-backed storage; the large media/download data stayed on the spinning disk, where sequential bulk storage actually belongs. I/O wait dropped to under 2% instantly.

Lesson

Separate your system disk from your bulk storage disk — especially if the bulk disk is spinning rust and anything on it does small random writes. Torrent clients and databases are exactly the workloads that will ruin an HDD's day.

Locking it down

With performance sorted, I went through and actually hardened the stack: blocked executable file extensions at the download-client level, added a release-profile blocklist in Radarr/Sonarr for known fake-release tags, set minimum file sizes per quality tier, and wrote a small cron script to auto-remove and blocklist anything stuck "stalled" for 72+ hours.

Also found — and fixed — a qBittorrent category pointing at a path that didn't correspond to any actual mount. It hadn't caused a problem yet, but the first time it triggered, files would have silently landed inside the container's ephemeral filesystem instead of anywhere persisted. A landmine worth defusing before it went off.

A reverse proxy, and two real bugs

Wanted friendly URLs for every service instead of remembering a dozen ports. Traefik was already sitting in the stack, so I wired it up with Docker-label routing and subdomains under a private domain, resolved through the Pi-hole already running on the network.

Getting there surfaced two bugs that had nothing to do with my config:

  • Traefik itself was broken before I even touched it. Docker 29 raised its minimum supported API version, and Traefik's client defaulted to a version so old it no longer worked — and didn't respect the usual environment-variable override. Only genuinely fixed in a specific later patch release, so a straight version bump wasn't enough; had to jump twice.
  • Traefik was non-deterministically picking the wrong Docker network for backends that sit on two networks at once. Some services proxied fine, others returned 504 because Traefik tried routing to a subnet it had no route to. Fixed with an explicit network label on every routed service, removing the ambiguity entirely.

Plex stayed off the proxy — it needs host networking for local discovery, which can't cleanly join a second Docker network, and it has its own remote-access system anyway.

The ratio lesson nobody warns you about

A quick disclaimer

BitTorrent is a protocol, not a crime — it's just an efficient way to move data, and plenty of legitimate uses run on it (Linux ISOs, game patches, open datasets, and the public-domain/self-hosted content this stack is built for). Piracy is a different thing, and it's illegal. Be smart, know your local laws, and follow the rules.

Got access to a private tracker and wanted it as the primary indexer. Set its priority to the top in Prowlarr, expecting that to settle it. It didn't — Sonarr kept grabbing lower-quality releases from public trackers instead.

Turns out indexer priority is a very weak, late-stage tiebreaker in Sonarr/Radarr's scoring — it only matters when releases are otherwise nearly identical. The actual fix was toggling Automatic Search off on the public indexers, leaving only the private tracker for automatic grabs.

Which is when it stopped grabbing anything at all. Chased what looked like a Prowlarr bug — a cryptic "invalid torrent file" parse error — all the way down to curling the tracker directly with my own session cookie, bypassing every proxy layer in between. The tracker's actual response:

# What the tracker actually said, once I stopped trusting the proxy's error message "Your ratio is dangerously low: 0.198 — You do not have permission to Download"

Not a bug anywhere in the stack. Just an account that had downloaded a lot more than it had ever seeded back — made worse by qBittorrent silently capping seed time at 60 hours, cutting torrents off long before they'd built up any real upload credit.

Lesson

A scraper-based indexer proxy will happily surface a cryptic parse error for what is actually a plain-English rejection from the source. When something fails mysteriously through a proxy, go straight to the source with the same credentials before assuming the proxy is broken.

Removed the seeding cap, enabled freeleech-only as a safety net, and left the public indexers back on as a working fallback while the ratio recovers the honest way — by seeding.

Where it stands now

  • ZFS pool on the old NAS box, mirror-ready for a second disk, ready to take on real redundancy
  • OS storage and media storage split across fast and bulk disks — the way it should have been from the start
  • Seven indexers behind Prowlarr, Cloudflare-protected ones included
  • A hardened, automated Radarr/Sonarr/qBittorrent setup instead of a pile of defaults
  • A reverse proxy that actually works, with real DNS instead of memorized ports

None of this started as a project. It started as "let me just check disk space real quick." If your homelab has taught you anything, it's that there's no such thing as "real quick."
