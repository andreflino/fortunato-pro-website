I Built a Fake Shop in My Homelab to Watch It Break (On Purpose)

End-to-end tracing with OpenTelemetry, a slow query hiding in two million rows, a cache, a queue, Kafka, and the classic "dual write" bug that quietly loses your users' emails

Most people use their homelab to run Plex. I also run Plex. But at some point you look at two little Proxmox boxes humming in the corner and think: what if I built a tiny online shop, wired it with the same observability tools big companies use, and then broke it in every way I could think of?

That's this post. No cloud bill, no pager, no angry customers. Just a fake shop that sells keyboards to a robot, and a lot of graphs.

What a homelab is actually good for

A homelab is a place where breaking production is encouraged. Mine is nothing fancy: a mini-STX box with a 2017 i5 and 20 GB of RAM, and a tiny Intel N150 mini PC that's mostly a NAS. Both run Proxmox. Neither will win any awards.

And yet on that hardware I'm running a monitoring stack that's architecturally the same thing you'd find at a mid-size company:

  • Prometheus for metrics (numbers over time: requests per second, latency, queue size)
  • Loki for logs (the text your apps print when they're happy or sad)
  • Tempo for traces (the story of a single request as it travels through the system)
  • Grafana to look at all three in one place, and jump between them

Every server in the house ships metrics and logs to it, including both Proxmox hosts (with SMART disk health, because that old Seagate isn't getting any younger). But monitoring servers is the boring part. The fun part is monitoring an application. So I built one.

Meet the shop

It's a small event-driven system: a handful of Python services that talk to each other through HTTP, a queue, and an event log. Here's the whole thing:

# Orders
loadgen ─▶ web ─▶ api ─▶ RabbitMQ ─▶ worker ─▶ Kafka ─┬─▶ notifier
                   │  ▲                  │            └─▶ analytics ─▶ Redis
                   ▼  │ cache            │
               Postgres ◀── Redis ◀──────┘ (invalidate)

# Signups (the dual-write lab, more on this later)
web ─▶ signup ─▶ Postgres (users + outbox) ─▶ outbox-relay ─▶ Kafka ─▶ email-service ─▶ inbox

# Telemetry
every service ─▶ OpenTelemetry Collector ─▶ Tempo + Loki, and Prometheus scrapes it

In plain words:

  • web is a very ugly HTML page where you place orders. Beauty was not a requirement.
  • api is a Flask API. It saves the order in Postgres and drops a "please process this" message into RabbitMQ.
  • worker picks the message up, "charges the card" (it sleeps for a bit, very realistic), updates the order, and announces the result on Kafka.
  • notifier and analytics both listen to Kafka. One pretends to email the customer, the other keeps a "top sellers" ranking in Redis.
  • loadgen is a robot that shops 24/7, so there's always something to look at. It's my best customer. It has never paid.

To keep things interesting, I added some sabotage: about 5% of orders get rejected by the API, 10% of payments get "declined", and there's a Slow queries button on the page that makes the database take a nap of 500 ms or 2 seconds before answering.

OpenTelemetry in 60 seconds

A trace is the full journey of one request. It's made of spans: each span is one step ("handle HTTP request", "run this SQL query", "publish to Kafka") with a start time, a duration, and some details attached.

The magic trick is context propagation. When the web service calls the API, it adds a header that says "hey, you're part of trace 4bf92f..., your parent is span 00f067...". The header looks like this:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^^ ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ ^^^^^^^^^^^^^^^^ ^^
       version  trace id (the whole journey)     parent span id   sampled

The API passes it along to RabbitMQ (inside the message headers), the worker reads it and passes it to Kafka, and so on. Every service adds its spans to the same trace. At the end you get one waterfall that shows the entire life of a click.

The best part: I wrote almost none of that code. Python's OpenTelemetry has zero-code instrumentation. Instead of python api.py you run:

opentelemetry-instrument python api.py

and it automatically patches Flask, requests, the Postgres driver, Redis, RabbitMQ, Kafka and logging. Configuration is just environment variables (OTEL_SERVICE_NAME=api, where to send the data, and so on). Every log line also gets the trace ID stamped on it, which is what makes the "jump from a log line to its trace" button in Grafana work.

Example 1: following one order from click to Kafka

Here's a real trace from the shop, simplified. One order, six services, one waterfall:

loadgen        POST /order
└─ web         POST /order
   └─ web      POST  → api
      └─ api   POST /orders
         ├─ api      INSERT orders                    (Postgres)
         ├─ api      INSERT order_events
         └─ api      orders send                      (RabbitMQ)
            └─ worker   orders receive
               └─ worker   process_order
                  ├─ charge_payment                   (pretend payment provider)
                  ├─ reserve_stock → SELECT ...
                  ├─ UPDATE orders
                  ├─ DEL cache:order:…                (Redis)
                  └─ order-events send                (Kafka)
                     ├─ notifier    send_email
                     └─ analytics   update_stats → ZINCRBY

When one of those 10% "payment declined" orders fails, the process_order span turns red. Click it, hit Logs for this span, and Grafana shows you the exact log line: order failed id=1ae71708 reason=payment_declined. Click that log's View trace button and you're back. That back-and-forth between logs and traces is the moment observability stops being a buzzword and starts being useful.

Tempo also builds a service graph from the traces, a live map of who talks to whom. I never drew that map. The system drew it for me by watching itself.

Example 2: the slow query hiding in two million rows

Every order has a history table, order_events. I stuffed it with two million rows of junk and "forgot" to add an index on order_id. So every time someone opens an order page, Postgres reads all two million rows to find the three that matter. Like looking for your keys by emptying every drawer in the house, every single time.

What's nice is that the same problem shows up in three independent places:

  • In the trace: one SELECT span is ~85 ms while everything around it takes about 1 ms. It sticks out like a sore thumb, and the span tells you the exact SQL.
  • In the metrics: Postgres's pg_stat_statements (exported to Prometheus) ranks that query as the top time-eater.
  • In the logs: Postgres logs every query slower than 50 ms, and those logs land in Loki.

The fix is one line:

CREATE INDEX ON order_events (order_id);

85 ms to under a millisecond. The trace span basically disappears. There is no feeling in software quite like fixing a performance problem with one line, and I recommend you engineer situations where you get to feel it.

Example 3: Redis, the cache that remembers (sometimes too much)

Next I put Redis in front of the order page using the cache-aside pattern, which is a fancy name for "check the fridge before going to the supermarket":

  1. Look for the order in Redis.
  2. If it's there (a hit), return it. Done.
  3. If not (a miss), ask Postgres, save the answer in Redis for 30 seconds, and return it.

The order page now tells you where the answer came from: "Served from database in 123 ms" the first time, "Served from cache in 4 ms" the second time. There's an on/off switch, hit and miss counters, and a cache.hit attribute on the trace span.

The tricky part of caching is never the caching. It's knowing when your cached copy is a lie. When the worker finishes an order, it deletes that order from Redis (invalidation). Comment that one line out and you get the classic bug: the page proudly shows "pending" for an order that completed 20 seconds ago. Everybody has shipped this bug at least once. Now you can ship it at home, safely.

Redis also does a second job here: the analytics service keeps a live "top sellers" ranking in a Redis sorted set. That data must never be thrown away, so Redis is configured to only evict keys that have an expiry (the cache), never the ranking. One setting, volatile-lru, and a whole category of "where did my data go?" disappears.

Queue vs. log: RabbitMQ and Kafka are not the same thing

I use both on purpose, because people mix them up all the time.

  • RabbitMQ is a to-do list. "Process order 42." One worker takes the task, does it, crosses it off. The message is gone.
  • Kafka is a newspaper. "Order 42 was completed." It's printed once, and everyone who subscribes gets their own copy, reading at their own pace. The notifier and the analytics service each read every event, independently.

That difference matters when things go wrong. Stop the notifier for two minutes and Kafka just remembers where it stopped reading. Its consumer lag (how far behind it is) climbs in Grafana while analytics keeps up perfectly. Start it again and it catches up from exactly where it left off. Nothing lost, nobody else affected. Try that with a to-do list.

The main event: the dual-write problem

This is the part I really wanted to build, because it's one of those bugs that hides in almost every system and almost nobody notices until a customer complains.

Imagine a signup flow. When someone signs up, two things must happen:

  1. Save the user in the database.
  2. Send a "please confirm your email" event to Kafka, so the email service sends the email.

Two writes, to two different systems. And here's the catch: there is no transaction that covers both. Postgres can't roll back a Kafka message, and Kafka can't roll back a database row. So if your process crashes between the two writes (a deploy, an out-of-memory kill, a network blip), they disagree forever.

It's like texting your friend "I'm on my way!" and then your car doesn't start. Your friend is waiting. Your car is not coming. Nobody is happy.

I built a signup service with three modes, a fake inbox (Mailpit) to receive the emails, and a "crash between the two writes" button. Here's what happened.

Mode 1: save the user, then publish

INSERT user; COMMIT        ✓ user saved
💥 crash
publish to Kafka           ✗ never happens

The user exists but the email never goes out. They can never confirm their account. They'll try again, get "email already registered", and go buy from your competitor. I call this a lost email. With a 100% crash rate, 3 signups gave me 3 users sitting in the database who will never hear from me.

Mode 2: publish first, then save the user

"Easy, just swap the order!" Nope.

publish to Kafka           ✓ email on its way
💥 crash
INSERT user                ✗ never happens

Now the email arrives, the user clicks the link, and gets "Account does not exist". A ghost email. Swapping the order doesn't fix a dual write. It just changes which way it breaks.

Mode 3: the transactional outbox

The fix is a well-known pattern called the transactional outbox, and it's beautifully simple: don't write to two systems. Write to one.

BEGIN;
  INSERT INTO users  (...);
  INSERT INTO outbox (topic, payload, ...);   -- "please send this event later"
COMMIT;                                        -- both rows, or neither

The event is saved as a row in the same database, in the same transaction as the user. If you crash, both writes roll back together. Then a small separate process, the outbox relay, reads unsent rows, publishes them to Kafka, and marks them as sent. If Kafka is down, the rows just wait patiently. Signups keep working.

But there's a twist. What if the relay crashes after Kafka accepted the message but before marking the row as sent? It wakes up, sees the row still unsent, and sends it again. The outbox guarantees at-least-once delivery, not exactly-once. So the email service has to be idempotent: every event has a unique ID, and the email service remembers which IDs it already handled. Seen it before? Skip it.

The scoreboard

The signup page reconciles the user table against the emails actually sent and counts the damage. These are the real numbers from my test runs:

SetupResult
Save first, then publish, crash every time3 lost emails out of 3
Publish first, then save, crash every time3 ghost emails out of 3
Outbox, crash every timeNothing saved, nothing sent. Consistent.
Outbox, relay crashing 30% of the time, idempotency on10 users, exactly 10 emails (6 duplicates caught and skipped)
Same, idempotency off10 users, 13 emails. Two people got the same email twice.

And because everything is instrumented, the lost, ghost and duplicate counts are metrics too. In naive mode you can literally watch the "lost emails" line climb in Grafana, which is a strangely satisfying way to see a bug.

Lesson

Any time your code writes to a database and sends a message, ask yourself: "what happens if we crash right between these two lines?" If the answer is "something bad, quietly", you have a dual write. The outbox pattern plus an idempotent consumer fixes it, and it only costs one extra table.

The bugs I hit along the way (the honest section)

Building a lab to demonstrate bugs is a great way to discover your own. Three that are worth sharing:

  • The database spans vanished. Tracing was on, but no SQL ever showed up in the traces. It turned out that passing cursor_factory=RealDictCursor to conn.cursor() quietly bypasses the OpenTelemetry Postgres instrumentation. Setting it once on the connection pool instead fixed it. Zero errors, zero warnings, just missing data. The worst kind of bug.
  • Traces snapped in half at Kafka. The Kafka instrumentation creates a "receive" span, but doesn't keep it active while your code handles the message. So every consumer started a brand-new trace, and my beautiful end-to-end waterfall was two sad halves. The fix: read the traceparent from the Kafka message headers and start the handler span with it. Now one signup is one trace with 15 spans across 3 services, including the async hop through the outbox. (Yes, I store the trace context in the outbox row too, so the trace survives sitting in a database table.)
  • My outbox relay got stuck in a loop. My first version published rows in batches of 10, one transaction per batch. With the relay crashing 30% of the time per row, a batch of 10 only gets through 0.710 ≈ 3% of the time. Every crash rolled back the "sent" marks for the whole batch, so the relay kept re-sending the same 10 emails forever. Ten users stuck pending, nineteen duplicates caught. Switching to one row per transaction fixed it instantly. I built a demo of a reliability pattern and immediately wrote a reliability bug. Peak engineering.

Want to try it?

The whole lab is open source: github.com/andreflino/otel-lab. It's one docker compose up, needs about 2.5 GB of RAM, and expects a Tempo + Loki + Prometheus stack to send data to (the README explains the few settings that matter). It comes with a list of exercises: find the slow query, break the cache, kill a consumer and watch the lag, take Kafka down and watch the outbox hold the line.

Where it stands now

  • Every server in the house, Proxmox hosts included, sending metrics and logs to one monitoring VM
  • A shop that traces a click all the way through HTTP, RabbitMQ, Kafka, Redis and Postgres
  • A slow query, a cache, a queue and an event log, each with an "off" switch and a way to break it
  • A signup flow that demonstrates the dual-write bug and its fix, with the damage measured in Grafana
  • A robot that has placed over a thousand orders and never paid for a single one

The point of all this isn't the fake shop. It's that the patterns and tools you use at work, end-to-end tracing, caching, event streaming, outboxes, idempotency, all fit on a couple of cheap boxes at home, where you're allowed to break them as many times as you like. And breaking things on purpose is still the fastest way I know to understand how they work.
